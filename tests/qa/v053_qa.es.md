### #70 — Exportación GGUF (q4_0 / q4_k_m / q5_k_m / q8_0 / f16 / f32)

**Estado:** PENDIENTE — requiere una máquina con GPU + llama.cpp compilado.

Prueba de humo planificada (ejecutar en una máquina con 4 GB+ de VRAM con TinyLlama-1.1B-LoRA en `./adapter`):

```bash
soup merge -a ./adapter -o ./merged
for q in q4_0 q4_k_m q5_k_m q8_0 f16 f32; do
  soup export --model ./merged --format gguf --quant "$q" \
    --output "./out/tinyllama.${q}.gguf"
done
```

Criterios de aceptación:
- Los seis archivos existen con un tamaño distinto de cero.
- Los tamaños de archivo aumentan de forma monotónica: q4_0 < q4_k_m < q5_k_m < q8_0 < f16 < f32.
- `llama-cli` puede cargar cada archivo y emitir al menos un token.

Cuando se ejecute, registra los tamaños + el tiempo del primer token a continuación.

## v0.53.2

### #71 — Pipeline de exportación ONNX (`soup export --format onnx`)

**Estado:** APROBACIÓN PARCIAL — prueba de humo con modelo pequeño ✅, TinyLlama-1.1B bloqueado por la
RAM del host durante el posproceso `onnx.load(load_external_data=True)`.

**Plataforma:** Windows 11, Python 3.10, torch 2.5.1+cu121, transformers 4.57.6,
optimum 2.1.0, RTX 3050 4 GB (la exportación a ONNX corre en CPU; la GPU no se usa).

**Prueba de humo 1 — `hf-internal-testing/tiny-random-gpt2` (~5 MB):**

```python
from optimum.exporters.onnx import main_export
main_export(
    "hf-internal-testing/tiny-random-gpt2",
    output="./out/tinygpt2_onnx",
    task="text-generation",
    trust_remote_code=False,
)
```

Resultado: **APROBADO** — completado en 25.8s, emitió 8 archivos, `model.onnx` = 0.62 MB,
todos los artefactos de tokenizador/config presentes.

**Prueba de humo 2 — `TinyLlama/TinyLlama-1.1B-Chat-v1.0` + LoRA(r=4,
target=`q_proj`,`v_proj`) → fusión → ONNX:**

```python
# load fp16 base, attach tiny LoRA, save adapter, merge_and_unload, save merged
# main_export(merged_dir, task="text-generation-with-past", ...)
```

Resultado: **PARCIAL** — base cargada ✅ (3.2s), LoRA adjuntado ✅, fusión ✅ (9.6s),
traza + serialización de ONNX ✅. El paso de posproceso
`onnx.load(model.onnx, load_external_data=True)` falló con **MemoryError**
al cargar de vuelta en RAM el archivo de tensores de datos externos (TinyLlama-1.1B fp32
es ~4.4 GB; el host no tenía RAM libre suficiente para mantener el modelo dos veces — una en
disco como `model.onnx_data` y otra en el `onnx.ModelProto` para el posprocesamiento).

**Veredicto:** La integridad del pipeline quedó probada con tiny-gpt2. La exportación completa de TinyLlama-1.1B
está limitada por la RAM del host (no es un error de `soup_cli` ni de `optimum`). Vuelve a ejecutarla en una
máquina con ≥16 GB de RAM libre para completar la validación de tamaños.

**Registrado:** 2026-05-13 (Wave 3 de la versión v0.53.2).

### Pruebas de humo de CPU del entrenador en vivo de v0.53.2 (Paso 6d)

**Estado:** APROBADO — ambos wrappers nuevos del entrenador entrenan de extremo a extremo en CPU.

**Plataforma:** Windows 11, Python 3.10, torch 2.5.1+cu121, transformers 4.57.6,
peft 0.x — `hf-internal-testing/tiny-random-gpt2` (base sólo con safetensors, evita
la barrera de seguridad de `.bin` de torch < 2.6).

**`ClassifierTrainerWrapper`:** dataset de sentimiento de 4 filas, num_labels=2,
batch_size=2, max_steps=2. setup() construyó `GPT2ForSequenceClassification` con
`problem_type=single_label_classification`. train() completó 2 pasos con
loss finito 0.787 en 0.66s.

**`DistillTrainerWrapper`:** dataset de chat de 4 filas, teacher=el mismo tiny-gpt2 (congelado,
verificado `requires_grad=False`), `distill_divergence=forward_kl`,
`distill_temperature=2.0`, batch_size=2, max_steps=2. setup() cargó student +
teacher, aplicó PEFT LoRA, construyó la subclase `_DistillTrainer`. train() completó
2 pasos con loss finito 3.479 en 1.79s — kernel KL ejercitado en compute_loss.

**Errores detectados + corregidos en Wave 3:**
1. `DataCollatorForLanguageModeling` no rellenaba (pad) las `labels` pre-tokenizadas
   (las filas de longitud variable fallaban durante el batching) → se cambió a
   `DataCollatorForSeq2Seq(label_pad_token_id=-100)`.
2. Desajuste de dispositivo en `_DistillTrainer.compute_loss`: HF Trainer movía automáticamente el
   student a CUDA en una máquina con CUDA mientras que el teacher (`device_map="cpu"`)
   permanecía en CPU; el forward del teacher fallaba en el `index_select` entre dispositivos →
   se añadió el puente `teacher_inputs.to(teacher_device)` + `teacher_logits.to(student_logits.device)`.
   Se añadieron guardas de regresión a nivel de código fuente en `test_v0532.py`
   (`TestDistillSourceLevelGuards`).

**Registrado:** 2026-05-13.

## v0.53.4 #83 — Prueba de humo en vivo de LLaMA Pro (Paso 6d)

**Estado:** APROBADO — `apply_block_expansion_if_configured` + `apply_llama_pro_freeze`
ejercitados de extremo a extremo sobre un `transformers.LlamaForCausalLM` real (CPU, pesos
aleatorios, 4 capas / 32 ocultas / 4 cabezas).

**Resultado:**
- `expand_model_blocks(model, 2)` clonó los últimos 2 bloques decodificadores, inicializó a cero
  `mlp.down_proj.weight` Y `self_attn.o_proj.weight` (verificado
  `abs().sum() == 0.0` sobre los tensores reales de PyTorch), los añadió a
  `model.model.layers`, incrementó `config.num_hidden_layers` de 4 → 6.
- `apply_llama_pro_freeze(model, 2)` congeló correctamente todos los parámetros de los
  4 bloques originales Y cada embedding / lm_head, luego descongeló sólo los 2 bloques
  añadidos.
- El forward pass sobre `LlamaForCausalLM` produjo logits finitos de forma
  `(1, 8, 128)` — se cumple la propiedad de inicialización de identidad (la residual inicializada en cero hace
  que el nuevo bloque sea inicialmente una operación nula sobre el flujo residual).

**También se verificó la ruta de fallo con forma distinta a LLaMA:** `expand_model_blocks` sobre
`hf-internal-testing/tiny-random-gpt2` (que usa `model.transformer.h` y no
`model.model.layers`) lanza `ValueError` con el mensaje accionable
"could not find decoder layers list on the model (expected
model.model.layers or model.decoder.layers)". Este es el fallo ruidoso esperado
para arquitecturas no admitidas — el esquema no bloquea `expand_layers`
por arquitectura, de modo que el usuario recibe un error de runtime claro si intenta LLaMA Pro
sobre una base con forma de GPT-2.

**Registrado:** 2026-05-13.

### #75 — Proveedores de datos sintéticos + trazas (backends en vivo)

**Estado:** PENDIENTE — requiere un colaborador con Ollama instalado localmente Y
la variable de entorno `ANTHROPIC_API_KEY`.

Prueba de humo planificada:

```bash
# Ollama (localhost-only — provider rejects remote URLs)
soup data generate --provider ollama --prompt "Five short Python tips" \
  --count 10 --output ./gen.jsonl

# Anthropic (env-only API key — never CLI arg)
ANTHROPIC_API_KEY=sk-ant-... \
  soup data generate --provider anthropic \
  --model claude-3-5-sonnet-latest --count 10 --output ./gen-claude.jsonl

# Augment via LLM
soup data augment --input ./gen.jsonl --output ./aug.jsonl \
  --strategy rephrase --count 2

# Trace harvester end-to-end (langchain JSONL → preference pairs)
soup data from-traces --input ./traces.jsonl --output ./pairs.jsonl \
  --judge --judge-provider ollama --min-confidence 0.7
```

**Criterios de aceptación:**
- `soup data generate` escribe JSONL válido con los campos `instruction`/`output`
  en formato alpaca; `messages` en sharegpt/chatml; el bucle se completa dentro del
  presupuesto de rate-limit sin 429s.
- `soup data augment` produce `count` variantes aumentadas por fila de entrada;
  rephrase preserva la semántica, translate cambia el idioma, style cambia el tono.
- `soup data from-traces --judge` llama al backend de judge exactamente dos veces por
  par (chosen + rejected) y escribe un campo `_judge_confidence` en cada
  fila conservada. La confianza ≥ 0.7 se conserva; por debajo del umbral se descarta.

**Cobertura de esquema + validadores** de la superficie de seguridad ya reside en
`tests/test_synth_data_pro.py` + `tests/test_v0403_part_c.py` (filtro `--judge`,
JudgeEvaluator simulado, proveedores verificados contra SSRF). El PENDIENTE aquí es
*observacional* — confirmar que los proveedores realmente llaman a los backends y
devuelven JSON bien formado cuando se invocan contra un Ollama local y una clave
de Anthropic reales.

**Registrado:** 2026-05-13 (versión v0.53.7).

### #71 — Pipeline completo de exportación ONNX de TinyLlama

**Estado:** PARCIAL — la primera mitad APROBADA, la segunda mitad limitada por RAM.

`soup export --format onnx --model TinyLlama/TinyLlama-1.1B-Chat-v1.0` ejecutó
`optimum.main_export` hasta la etapa de traza + serialización; el
paso de posproceso `onnx.load(load_external_data=True)` necesita mantener el
blob completo de pesos fp32 de ~4.4 GB en RAM junto con el archivo serializado. La máquina de desarrollo
tiene 8 GB; se quedó sin memoria (OOM). La exportación ONNX de Tiny-gpt2 (300 MB) APROBADA de extremo a extremo.

**Mitigación:** Las exportaciones ONNX más grandes necesitan un host con 16 GB+ de RAM. El envoltorio de Soup es
correcto; este es un techo de RAM del host, no un error de Soup. Registrado para futuro QA
en una máquina más potente.

**Registrado:** 2026-05-13 (versión v0.53.7, reconfirmado desde la entrada de v0.53.2).

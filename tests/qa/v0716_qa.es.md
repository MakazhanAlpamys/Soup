## #75 — QA de datos sintéticos (`data from-traces` / `data augment` / `data generate`)

### `soup data from-traces` (sin proveedor — offline) — APROBADO
Se construyó un JSONL de trazas de OpenAI con una salida con pulgar arriba y otra con pulgar abajo para
el mismo prompt:

```
soup data from-traces --logs traces.jsonl --format openai --signal thumbs_up -o pairs.jsonl
```
→ `Wrote 1 preference pair(s)`; el par es una fila
`{prompt, chosen, rejected, source}` correcta. Se imprimió el panel de recordatorio de PII. ✅

### `soup data generate` (Ollama en vivo) — APROBADO
```
soup data generate --provider ollama --model qwen2.5:0.5b -p "Write a short factual Q&A about Python lists" -n 1 -o gen.jsonl
```
→ `Generated 2 examples`, formato alpaca, contenido razonable (preguntas y respuestas de list vs tuple). ✅

### `soup data augment` (Ollama en vivo) — **ERROR ENCONTRADO + CORREGIDO**
La primera ejecución lanzó `ImportError: cannot import name 'OllamaProvider' from
soup_cli.data.providers.ollama`. Causa raíz: `_load_augment_provider`
(`commands/data.py`) construía clases `OllamaProvider` / `AnthropicProvider` /
`VllmProvider` que **nunca existieron** — los módulos de proveedores entregan
*funciones* (`generate_ollama`, `validate_ollama_url`, …). Así que `data augment`
estaba roto para **los tres** proveedores desde v0.25.0, Y codificaba
`llama3.1:8b` sin bandera `--model`.

Corrección (v0.71.6 #75): `_load_augment_provider` ahora devuelve un adaptador
`_AugmentProvider` que delega en el `make_judge_provider_fn` reforzado de v0.53.7
(URLs validadas contra SSRF, clave de Anthropic sólo por entorno) y desenvuelve `{"text": …}` al
contrato `.generate(prompt) -> str` que esperan las estrategias de augment. Se añadieron
las opciones `--model` / `--base-url`. Tras la corrección:
```
soup data augment -i in.jsonl -o out.jsonl --strategy rephrase --provider ollama --model qwen2.5:0.5b --count 1
```
→ `Augmentation complete: 1 → 2 (rephrase via ollama)`. ✅ El pipeline corre
de extremo a extremo. (Observación, no un error: `qwen2.5:0.5b` es lo bastante pequeño como para que su
salida de rephrase a veces repita la entrada palabra por palabra — un artefacto de la calidad del modelo,
no un problema de cableado. Un modelo más grande produce paráfrasis visiblemente variadas.)

Cobertura de regresión: `tests/test_v0716.py::TestAugmentProviderFix`.

## #231 — runner de `soup build` en vivo — APROBADO
DAG de 3 etapas (`raw` semilla incremental → `clean` drop_empty incremental →
`counted` tabla token_count):

Primera ejecución materializó `raw` (3 filas), `clean` (2 filas tras drop_empty),
`counted` (`n_tokens` añadido). La reejecución tras cambiar una fila de origen mostró que
la optimización incremental funcionaba:
```
raw     incremental  rows_in=3 rows_out=3 transformed=1  +0 ~1 -0 =2
clean   incremental  rows_in=3 rows_out=3 transformed=1  +0 ~1 -0 =2
counted table        rows_in=3 rows_out=3 transformed=3  —
```
`transformed=1` demuestra que sólo se volvió a ejecutar la fila cambiada; las 2 filas sin cambios
se conservaron desde el almacén de estado de SQLite. ✅


instrucciones de usuario a partir del prefijo desnudo `<|im_start|>user\n` y las correspondientes
respuestas del asistente mediante la finalización cruda de `/api/generate`. ✅ Verdadero
Magpie de recolección por prefijo contra un modelo en vivo.

## #213 — IRT 2PL / 3PL — APROBADO
Matriz de respuestas: 6 encuestados × {`const` (siempre correcta), `split` (umbral
de habilidad limpio), `easy`}.
```
soup eval irt-subset resp.jsonl --size small --model 2pl   → selects ["split"]
soup eval irt-subset resp.jsonl --size tiny  --model 3pl   → runs, guessing bounded
```
El ajuste 2PL selecciona correctamente el ítem más informativo (`split`, el umbral
equilibrado) por encima del ítem `const` de información cero. La falta de `respondent_id` en una
ejecución 2PL/3PL falla con un `IRT fit failed: rows[0] missing
respondent_id` amigable (salida 2). 1PL se mantiene en la ruta de un solo encuestado
`{item_id, correct}` (compatibilidad retroactiva). ✅

# FlashAttention / Liger: H200 sequence and checkpointing sweep

Measurement for [#378](https://github.com/MakazhanAlpamys/Soup/issues/378),
2026-11-10, source `311962ced65176d9adb05a0a6c875b5785c1a2b8`.
This is a second Hopper/current-stack record. It does not reproduce or replace
the earlier H100 operating point, and changes no product code or default.

## What completed

All 32 sequence/checkpoint/implementation cells are accounted for: **24 successful
activation probes and 120 successful timing processes**, plus **8 probe OOMs**
whose 40 timing slots are retained as `not_run_probe_oom`. Five repetitions per
feasible cell; no failed or slow timing was dropped. The grid took about
5 h 44 min, from 15:01 to 20:45 UTC, including probes, setup and model reloads.
That campaign duration is not the throughput denominator.

Liger alone measured **1.197-1.229x** SDPA throughput at the feasible operating
points, with **21.6-54.7%** less peak allocated memory. Separate FA2 measured
**0.929-0.989x** SDPA, with effectively the same allocated peak. FA2+Liger
measured **1.096-1.195x** SDPA, below Liger alone in every feasible cell.
These are ratios of five-run medians on this model, fixture, stack and shared
card, not universal speedups or a training-quality recommendation.

## Fixed method and machine

The [predeclared protocol](protocol-378-h200.md) and executable
[sweep driver](harness/issue378_sweep.py) / [worker](harness/issue378_flash_liger.py)
contain the complete recipe. All four arms run real Soup SFT setup and
`Trainer.train`, Llama-3.1-8B snapshot
`d04e592bb4f6aa9cfee91e2e20afa771667e1d4b`, BF16 resident base, FP32 LoRA
r16/alpha32/dropout0 on q/k/v/o/gate/up/down, batch4, accumulation1, AdamW
2e-5/constant, seed/data_seed378. No CPU offload, padding, packing or per-arm
tuning. The fixed telescope conversation is response-only; the actual collated
[4,S] token IDs and labels, not just source dataset columns, are hashed and
checked across arms at each operating point.

One fresh process per arm, a cyclic rotation of arm order in each repetition,
**5 warm-up updates + 80 synchronized measured updates**, optimizer included.
Input tok/s = `4 * S * 80 / sum(measured step seconds)`: it counts input tokens,
not only supervised targets. The timer surrounds Trainer's step callbacks; it
excludes loading, preceding data-loader fetch, between-step logging and saving.
This is not full `soup train` wall time. Raw rows also keep total Trainer time,
every step duration, training loss, steady allocated peak and reserved peak.
The table's allocated peak covers all training, including resident parameters,
optimizer and warm-up. It is not `nvidia-smi` whole-card memory.

Physical GPU2: NVIDIA H200, 143771 MiB, UUID
`GPU-6b984734-8ed6-11dd-3b9a-0b6c36ba5e11`. An unrelated idle process
held **49850 MiB** before every run, leaving about 90 GiB headroom. Its
allocations are not included in the process allocator peak. No other process,
GPU clock, power limit or allocator setting was changed. Every raw row has
sampled clocks, temperature, power and whole-card utilization. Clock ranges
below include each process's initial idle sample, as well as training samples.
The card was shared; these are not exclusive-card causal measurements.

Python3.12 / torch2.14.1+cu130 / CUDA13.0 / Transformers5.19.0 / TRL0.29.1 /
PEFT0.21.2 / Triton3.8.0 / Liger0.8.5 / FA2 2.8.3.post2. The isolated FA2 build
needed C++20 flags for these torch headers; only four setup compiler-standard
arguments changed, no kernel or dispatch code. The source/build hashes and
FP64 sanity results are retained in
[preflight evidence](evidence/flash-liger-378-preflight/).

## Activation, numerics and limitations

Separate eight-step probes for **every feasible cell** assert actual SDPA/FA2
calls and executed Liger module classes. For example S1024/checkpoint-off
records 256 SDPA calls and zero FA2 in the baseline; FA2 reverses those counts;
Liger arms execute 520 RMSNorm and 256 SwiGLU calls. Timing processes have
counters and profiling disabled. The S1024 baseline profiler includes
`ScaledDotProductCudnnAttentionBackward0` and cuDNN SM90 flash-attention kernels.
So the comparison is an already-fused native SDPA path against standalone FA2,
not naive quadratic materialization against flash attention.

FA2's independent FP64 causal-GQA forward/backward sanity check passed its
predeclared relative-L2 limits (worst BF16 0.306%, FP16 0.038%). The initial
BF16-SDPA elementwise check failed one K/V-gradient element and remains in the
preflight record. This is **not bit-exact equivalence** or full-model gradient
parity. Full training losses are retained, but no held-out quality evaluation
was run. This repetitive synthetic fixture is a measurement instrument, not
proof that all paths learn the same quality. The existing Liger path disables
Soup's logits-based rewind recorder because its fused CE exposes no logits;
this record does not conceal or change that behavior.

All checkpoint-off S4096 and S8192 probes OOMed. For example S4096/SDPA reports
89.76 GiB allocated by PyTorch, another process holding 48.68 GiB and only
133.69 MiB free when a 448 MiB allocation failed. **An OOM here is a shared-session
headroom failure, not an unconditional H200 capacity limit.** No timings,
activation success or ratios are fabricated for those cells. Checkpoint-on
completed at every requested sequence length. A dedicated-card run is needed
to fill the checkpoint-off long-sequence timings.

## Raw record and reproduction

The repository retains the
[protocol](evidence/flash-liger-378-h200/protocol.json),
[validated summary](evidence/flash-liger-378-h200/summary.json),
[environment](evidence/flash-liger-378-h200/environment.json), the build/math
qualification summaries and one
[manifest](evidence/flash-liger-378-h200/manifest.json). The manifest records a
SHA-256 and byte count for every original raw file, plus the versioned archive
URL, archive SHA-256 and retained-file checksums. The original campaign did not
save a driver-version string or configured power-limit wattage; the environment
marks those fields as unrecorded rather than substituting a later observation.

All **203 original files**, including 32 probes, all 160 timing slots, preflight
pilots and the original checksum list, are preserved byte-for-byte in the public
[raw-evidence archive](https://github.com/AubakirovArman/Soup/releases/download/benchmark-flash-liger-h200-2026-11-10-02d25f35/flash-liger-h200-2026-11-10-02d25f35.tar.gz).
Its SHA-256 is
`2236ca71d850db879d1132049c7a84a104d6a31ee257b4a978dd584cb112cbd5`.
OOM JSON includes its traceback. Successful JSON includes the realized batch,
workload hashes, model snapshot, source/worker identity, versions, module/call
activation evidence, losses, step timings and telemetry. Moving these files does
not replace or rerun any measurement.

The CPU-only check works on the retained summary without downloading the bulk:

```bash
python benchmarks/harness/flash_liger_record.py
pytest tests/test_flash_liger_sweep_protocol.py tests/test_flash_liger_record.py --no-cov
```

It checks retained-file hashes, grid completeness, ranges and ratios, and prints
that raw files were not supplied or checked. To recheck the full record, download
the archive, verify its SHA-256 against the manifest, and extract it into a fresh
directory containing `flash-liger-378-h200/` and `flash-liger-378-preflight/`.
Then request raw verification explicitly:

```bash
python benchmarks/harness/flash_liger_record.py --raw-root /tmp/soup-378-evidence
```

That mode checks every raw-file hash and recomputes the summary with the original
sweep summarizer. A requested but absent or corrupted raw file fails; it never
silently falls back to a summary-only pass. Neither check is a GPU rerun.

Follow the protocol's commands in a compatible isolated environment to run a
new campaign. Resume requires the same source commit and worker hash; do not
mix a different checkout into an existing campaign. The original private machine
paths in the protocol are recorded provenance; use your own pinned model-snapshot
path for a new campaign.

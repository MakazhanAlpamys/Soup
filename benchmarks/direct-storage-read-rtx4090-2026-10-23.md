# Native NVMe-to-GPU read probe on Linux

## Question

Can Linux GPUDirect Storage deliver bytes from a physical NVMe drive to CUDA
device memory, with a verifiable native route? If verified, how would it compare
with unbuffered disk reads into pinned host memory followed by a synchronized
host-to-device copy?

## Environment

The controlled attempt ran on 2026-10-23 on an NVIDIA GeForce RTX 4090 with
driver 595.91.07, in a CUDA 12.8.1 development container based on Ubuntu 22.04.
The data mount was XFS on local `nvme0n1p3`. The result packet omits the host
CPU model, host RAM, GPU VRAM capacity and host kernel version. The native
C++/CUDA probe used the SDK's cuFile with route statistics disabled. The
packet gives the SDK image and the CUDA runtime and driver API version
integers below. The separate cuFile package and Python tooling versions
are unspecified. The fixture was raw SHAKE256-generated bytes.
Model, tensor dtype and torch were inapplicable.

## Harness and controls

The `direct_probe.cpp` native executable compiled and linked against the real
CUDA SDK. The Python driver prepares the deterministic fixture, builds the
executable, launches fresh processes and independently audits the copied bytes.
The capability path runs one read per process with no timed warm-up. The
recorded build and capability modes were:

```sh
python benchmarks/harness/g3_probe.py prepare --work "$SESSION/work"
python benchmarks/harness/g3_probe.py build --out "$SESSION/build" \
  --cuda-root /usr/local/cuda --stats off
python benchmarks/harness/g3_probe.py capability --phase capability \
  --work "$SESSION/work" --build "$SESSION/build" \
  --authority "$SESSION/authority.json" --controls "$SESSION/controls/calibration.json" \
  --commit 50cbebde583e74fa50184b9dc35c6f96b4c50ac5 \
  --rule-sha 49878ed2eee7835b0bc4aaffc3a19660a804dd0799a02533dad5dd6f822ec292
python benchmarks/harness/g3_probe.py audit --out "$SESSION/work/capability_001"
```

The disk sensor recognized clean and owned reads and rejected an independent
1.25 GiB foreign read. The capability sequence used four fresh processes in
control, direct, direct, control order. The two controls used aligned unbuffered
reads, pinned staging and synchronized CUDA copies. Each returned the entire
device buffer to host for comparison with the fixture oracle. All four
processes passed the suspend, power, foreign-read and GPU-clock checks.

**Verdict: BLOCKED.** cuFile driver initialization failed twice. Native direct support has no verdict, and the comparative performance phase never ran.

## Limitations

The installed cuFile header associates error 5001 with an unavailable
`nvidia-fs` driver. The older SDK used a predeclared statistics-off mode that
could not certify the transfer route. Other Linux attempts found unsuitable
storage topology or lacked the configured native driver, counters or diagnostics.
The study skipped the compatibility fallback. The controls establish byte
correctness for the staged path on this setup. Bandwidth, CPU cost, total
pinned host RAM and concurrent two-drive behavior remain unmeasured. Guest
instrumentation could only assess isolation visible inside the guest. This
record covers the Linux native path.

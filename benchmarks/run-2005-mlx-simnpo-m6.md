# Native SimNPO unlearning on MLX, qualified on an Apple M6

Filed against [#2005](https://github.com/MakazhanAlpamys/Soup/issues/2005).
It asks one question: on a real Llama-architecture checkpoint, does
`task: unlearn` with `unlearn_method: simnpo` on `backend: mlx` lower the
measured likelihood of a defined forget set, more than it lowers the likelihood
of unrelated text, with an adapter that reloads in a fresh process?

It does not establish erasure, privacy protection or compliance, and it says
nothing about other architectures, quantized bases, larger models or other
settings than the ones below.

## Configuration

| | |
|---|---|
| Machine | Apple M6, 24 GB unified memory |
| OS / Python | macOS 27.0.1, arm64, Python 3.12.14 |
| MLX | `mlx` 0.32.4, `mlx-lm` 0.32.2 |
| Checkpoint | [`HuggingFaceTB/SmolLM2-360M-Instruct`](https://huggingface.co/HuggingFaceTB/SmolLM2-360M-Instruct) at revision `a10cc1512eabd3dde888204e902eca88bddb4951` (`model_type: llama`, bf16), a local snapshot |
| Config | `backend: mlx`, `task: unlearn`, `unlearn_method: simnpo` (beta 0.1, gamma 0), `unlearn_alpha` omitted (1), LoRA r=8 alpha=16 dropout 0 on the default modules, `lr: 1e-4`, `epochs: 3`, `batch_size: 2`, `gradient_accumulation_steps: 1`, `max_length: 128`, `quantization: none`, everything else default |
| Seeds | 0, 1 and 2 (`training.seed`) |
| Harness | [`harness/mlx_simnpo_qualify.py`](harness/mlx_simnpo_qualify.py) |

**The rows** are generated by the harness, `prompt`/`completion` pairs:

- `forget_train`, 24 rows on one topic, the planet Mars: the `forget_set`;
- `forget_heldout`, 12 other rows on Mars, some asking about the same facts in
  other words; never trained on;
- `retain_train`, 24 rows on unrelated general knowledge: the `retain_set`;
- `retain_heldout`, 12 other unrelated rows; never trained on.

24 forget rows at `batch_size` 2 for 3 epochs is 36 updates per run.

**The arms**, each scored in a fresh process of the harness:

- `base`: the checkpoint as `mlx_lm.load` returns it;
- `untrained`: the checkpoint with the run's LoRA layers attached from its
  `adapter_config.json`, not trained. LoRA's B starts at zero, so this arm
  should score as `base` does, and it checks the plumbing the adapter arm
  goes through;
- `adapter`: `mlx_lm.load(base, adapter_path=<run output>)`.

The trained model is also scored in the training process, right after
`train()` returns.

**The measure** is the per-token negative log-likelihood of each set, in nats:
the summed NLL of every row's target tokens (the completion and EOS) divided by
the number of them, pooled over the set's rows. Every row is tokenized by the
trainer's own `build_unlearn_example` and scored alone, with no padding, from
float32 logits through a NumPy float64 log-softmax. A rise in NLL is a fall in
likelihood. `ΔNLL` is `adapter` minus `base`.

## The rule

Written before the first run, and applied by the harness's `verdict()`
unchanged. **PASS** only if every check holds on every seed; otherwise
**FAIL**, published with its numbers.

1. **Dispatch:** `build_trainer` returns `MLXSimNPOTrainerWrapper`, asserted
   before anything is measured.
2. **Updates:** the run reports the 36 updates the configuration implies.
3. **Control:** the `untrained` arm's NLL is within 0.001 of `base` on all four
   sets.
4. **Reload:** the `adapter` arm's NLL is within 0.01 of the in-process score on
   all four sets.
5. **Forgetting:** `ΔNLL(forget_heldout) ≥ +0.5`.
6. **Selectivity:** `ΔNLL(forget_heldout) − ΔNLL(retain_heldout) ≥ 0.5`.
7. **Retain bound:** `ΔNLL(retain_heldout) ≤ +0.25`.

The settings above are the only ones run before this rule's result is recorded.
If the result is FAIL, it stays the result: a later run with other settings
would be a new record with a rule of its own.

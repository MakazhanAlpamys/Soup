- **`soup ui` no longer keeps its auth token in `sessionStorage` or on `window._authToken` (#1136 by @mohdUwaish59 in #1190).** The Web UI now holds the token in a closure in `app.js`, and every request goes through one `authFetch` wrapper that adds the `Authorization` header without exposing the token to other page script. The token is deliberately not persisted: a reload or a new tab asks for it again (paste the token `soup ui` printed), where before it was restored from `sessionStorage`. This narrows the gap between a future rendering mistake and a token disclosure; it does not stop script already running in the page, for which the Content-Security-Policy remains the defence. A fresh desktop browser can now sign in at all: `soup ui` opens its URL without a token, and on 0.75.0 and 0.75.1 nothing in the page asked for one, so every panel stayed at 401; the page now prompts on the first 401 and accepts the pasted token or the whole `Authorization: Bearer …` line. `authFetch` also refuses cross-origin URLs, so the header only ever goes to the UI's own origin. The chat request no longer sends an empty `Bearer ` header when no token is held.

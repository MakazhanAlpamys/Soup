- **Tasks that never apply `training.quantization` no longer record a quantised run, and an explicit `4bit` or `8bit` on them is deprecated; Soup v0.76 will refuse it (#795 by @Srinivasan8888 in #1043).** `distill`, `classifier`, `reranker`, `cross_encoder`, `prm`, `moe_lora_routing`, `unlearn` and `asr` never quantise their models, yet accepted the default `4bit`, stored it in the run's config, and let the VRAM pre-flight budget them as QLoRA jobs. For these tasks the default changes: an unset `quantization` now resolves to `none`. An explicit `4bit`, `8bit` or `load_in_8bit: true` still loads, because every config Soup dumped on the old default carries `quantization: 4bit` literally, but it prints a warning naming the task, resolves to `none`, and will be refused in v0.76; set `quantization: none`. A Quant Menu value or a 4-bit-only setting such as `bnb_4bit_quant_storage` is refused at config load, naming the task. PRM also refuses a `lora` block it never reads (`lora.r: 0` is allowed), and the pre-flight budgets PRM, and the classifier family and ASR without their LoRA opt-in, as full fine-tunes. `docs/training.md` lists which tasks honour the field.

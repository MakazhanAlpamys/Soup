- **`training.loraplus_lr_ratio` was silently ignored on every LoRA task except
  sft, pretrain and embedding (#1080 by @abdulwaarith0).**
  #724 routed LoRA+ through `attach_loraplus_optimizer` (the ratio is a PEFT
  optimizer setting, not a `TrainingArguments` field) but wired only the three
  SFT-family trainers. Every other trainer that builds a LoRA adapter (asr, bco,
  classifier, distill, dpo, grpo, ipo, kto, orpo, ppo, reward_model, simpo)
  accepted `loraplus_lr_ratio` and then trained without it. After #724 the option
  no longer crashed on those tasks, so a preference or RL run could set the ratio,
  show a normal loss curve, and train the LoRA B matrices at the base learning
  rate rather than `lr * loraplus_lr_ratio`. Eleven of the twelve now attach the
  LoRA+ optimizer once the trainer is built, so B trains at `lr * loraplus_lr_ratio`
  and A at `lr`, the same as the SFT family. PPO is wired differently: its
  `trl.experimental` trainer builds the optimizer and scheduler eagerly in
  `__init__`, so the LoRA+ optimizer is built up front and passed to the
  constructor as `optimizers=(opt, None)`, because a post-construction attach would
  train B at a flat `lr * loraplus_lr_ratio` with warmup and decay never reaching
  it. This changes training results: any run that set `loraplus_lr_ratio` on one of
  those tasks now produces different weights than before, because the B matrices
  learn at the higher rate that was requested.
  `unlearn` is the one LoRA task that cannot be wired: it drives its own
  `torch.optim.AdamW` loop instead of a `Trainer`, so there is no optimizer to
  attach to. Setting `loraplus_lr_ratio` with `task='unlearn'` is now refused at
  config parse, naming the remedy, rather than being silently dropped. A source
  scan (`tests/test_issue724_loraplus_wiring_coverage.py`) fails if a new LoRA
  trainer ships without either wiring LoRA+ or being given a documented exemption.

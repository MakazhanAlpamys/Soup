- **One peak-VRAM estimate for `soup train`'s pre-flight, `soup profile`, the MCP `profile` tool and `soup plan` (#2049 by @abdulwaarith0 in #2146).** The pre-flight and `soup profile` priced the same run with two formulas in two units, and neither charged the logits and loss chain, which decides long, large-vocabulary runs. All four now use `utils/vram_estimate.py`, which reads the model's `config.json` and safetensors headers (never the weights) and prices weights, adapters, gradients, optimizer state, activations, logits, the 4-bit dequantization copy and overhead, calibrated on 39 measured runs (`benchmarks/gate-2049-resident-vram.md`). The pre-flight now refuses some long-sequence, large-vocabulary runs and some runs without gradient checkpointing that it let through; `--allow-oom-attempt` still launches them. `soup profile`'s numbers change, and its JSON gains the exact bytes per term, the fit verdict and where the model's shape came from. `soup plan` records `peak_vram_gb: null` with a `peak_vram_reason` when it cannot price the run, instead of a fixed 8.0 GB; a state file written before this still loads.

- Custom eval task files now refuse a row whose `expected` is missing, `null`, or empty or whitespace-only, under every `scoring`, naming the line: `Line N: field 'expected' is missing`, `Line N: field 'expected' is null` or `Line N: field 'expected' is empty or whitespace-only`. Under `contains` and `regex` such a row scored 1.0 for every output, an empty one included, so an eval gate built on it passed for a model that answered nothing and could never regress; under `exact` it matched only an empty output, and under `semantic` and the `tool_call_*` scorings it scored 0.0. The refusal reaches every caller that scores `expected`: `soup eval custom` (exit 1), `soup eval quant-check` and `soup eval retention` (exit 3), eval gate `type: custom` tasks (the task fails with the message), the `soup ship --task-eval` metric leg and its noise floor, the `cmaes` merge scorer, the deploy measure and the `soup loop --verify ship` check. `soup ship --task-mode judge_score`, `pairwise` and `reward` never score `expected`, so a prompt-only file stays valid there. Numbers and booleans keep loading as their text (`4`, `0`, `False`). Migration: a task file with such a row loaded on 0.78.0 and is refused now; give each row an `expected`, or remove the row. Nothing measured is lost: those rows scored 1.0 for any output, or matched the word "None". A `soup eval retention` ledger that registered a control file with such a row cannot continue: the file is refused at load, a corrected copy no longer matches the recorded SHA-256, and every run checks every registered control file, so registering the corrected copy under a new task name still stops at the old one. Start a new ledger (`--ledger`) with the corrected file; under `contains` and `regex` the old ledger's scores on that task counted those rows as passed for any answer (#3240 by @abdulwaarith0 in #3268).

- Custom eval task files now refuse a row whose `expected` is missing, `null`, or empty or whitespace-only, under every `scoring`, naming the line: `Line N: field 'expected' is missing`, `Line N: field 'expected' is null` or `Line N: field 'expected' is empty or whitespace-only`. Such a row used to load (`answer` already refused a missing or blank one). A missing or empty `expected` scored 1.0 for every output, an empty one included, under `contains` and under `regex` (an empty pattern matches anywhere), and `contains` also stripped a whitespace-only one to nothing, so an eval gate built on such rows passed for a model that answered nothing and could never regress. A `null` one loaded as the text `None` and matched any output containing that word. The refusal reaches every caller that scores `expected`: `soup eval custom` (exit 1), `soup eval quant-check` and `soup eval retention` (exit 3), eval gate `type: custom` tasks (the task fails with the message), the `soup ship --task-eval` metric leg and its noise floor, the `cmaes` merge scorer, the deploy measure and the `soup loop --verify ship` check. `soup ship --task-mode judge_score`, `pairwise` and `reward` still accept a prompt-only file: the judge modes take their reference from `--judge-reference`, validated on its own, and the reward function receives `expected` as `answer`, empty when the row has none. Numbers and booleans keep loading as their text (`4`, `0`, `False`). Migration: a task file with such a row loaded on 0.78.0 and is refused now; give each row an `expected`, or remove the row. A `soup eval retention` ledger that registered a control file with such a row cannot continue: the file is refused at load, a corrected copy no longer matches the recorded SHA-256, and every run checks every registered control file, so registering the corrected copy under a new task name still stops at the old one. Start a new retention record (`--ledger`) with the corrected file (#3240 by @abdulwaarith0 in #3268).

- **A frozen LoRA base on a CPU without native bf16 units now loads float32 instead of the checkpoint's own dtype.** `resolve_frozen_base_load_dtype` used to return `"auto"` on every CPU, so a bf16-saved checkpoint loaded bf16 and every base matmul fell back to bf16 software emulation on x86 CPUs without AVX512-BF16/AMX (Ryzen, pre-Ice Lake Xeon, EPYC Zen 1-3) — measured 11.5x slower end-to-end (1005 s/it → 87 s/it, ~1.0 → ~11.7 tok/s) on a Ryzen 2600 running the TinyLlama-1.1B LoRA smoke, with val loss unchanged (1.5947 vs 1.6003). A CPU whose bf16 units are native keeps loading the checkpoint's dtype as before — those CPUs are not emulating, and float32 would double the frozen base's resident bytes for no throughput gain, which is the memory cost to weigh on a memory-constrained box. CPU training was previously documented as smoke-test-only, so the throughput cost never surfaced. CUDA and MPS resolution paths are untouched (#3164).

- **The OTLP tracing endpoint validator now rejects abbreviated, decimal, hex,
  and octal IPv4 forms, closing a bypass `#600`/`#604` never reached (#616 by
  @SID-6921 in #625).** `utils/tracing.py`'s `_is_private_ip` predated the
  #604 fix and was never folded into it: it had no `socket.inet_aton`
  fallback, so `soup serve --otlp-endpoint https://127.1:4317` (and the
  decimal/hex/octal equivalents) reached `validate_otlp_endpoint` as
  "not private" and sailed through. Found while consolidating the SSRF
  loopback/private-host predicate that had drifted into **six** copies
  across `hf.py`, `hubs.py`, `webhooks.py`, `loop_stages.py`, `qr_url.py`,
  and `tracing.py` (issue #616 originally counted three/four; an AST walk
  during review found the real count). All six now import one definition
  from the new `utils/net_guard.py`. Two behaviour changes fell out of
  the merge, both strictly more restrictive: `hf.py`/`hubs.py`/
  `loop_stages.py`/`qr_url.py` now also reject reserved and multicast IPs
  (previously only `webhooks.py` did), and `tracing.py` gains the
  abbreviated-IPv4 rejection above. A guard test (`ast`-walks
  `src/soup_cli/` for any function ending in `is_private_or_link_local` or
  constant ending in `LOOPBACK_HOSTS`, matching the leading-underscore
  spelling every original copy used) fails the build if a duplicate
  reappears. A seventh copy of the parsing logic, `loop_stages
  ._endpoint_is_local` (the deploy-canary SSRF guard), had the same
  abbreviated-IPv4 gap; it now shares `net_guard.parse_ip_literal` while
  keeping its own narrower policy (no reserved/multicast) rather than
  adopting the wider shared predicate, since that would change what the
  deploy surface trusts as a local target, not just where the logic lives.

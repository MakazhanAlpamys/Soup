- **`soup serve --backend transformers` honours the OpenAI `stop` parameter and Anthropic `stop_sequences` (#2549, #PRNUM).** Both were dropped before: a client that sent `"stop": ["\nUser:"]` got the text after the stop string, with `finish_reason` set as if no stop was asked for. `stop` on `/v1/chat/completions` takes a string, a list of at most four strings, or `null`; an empty list means no stop; `stop_sequences` on `/v1/messages` takes a list of at most four strings. An empty string, a non-string entry, more than four entries or an entry over 256 characters is a 400 whose message names the field. The reply is cut before the first stop string that completes (the stop string is not returned), `finish_reason` is `stop`, and `/v1/messages` answers `stop_reason: "stop_sequence"` with `stop_sequence` echoing the match (the reply now always carries a `stop_sequence` field, `null` when none matched). Whitespace left before the cut is dropped, as it is from the end of an uncut reply. A streamed reply holds back the last characters that could start a stop string (one fewer than the longest) and any trailing whitespace, ends generation at the match, and sends the held text when the reply ends without one, so the joined deltas equal the non-streamed reply. Generation is ended at the stop string on the plain `generate` path; with a draft model, n-gram lookup, beam search, `--reasoning-parser` or MoLE the full reply is generated and then cut. `X-User-Id` and `X-Conversation-Id` now reach `/v1/messages` generation as they do on `/v1/chat/completions`. The vLLM, SGLang and MII backends still ignore `stop`.

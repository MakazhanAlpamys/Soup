- **The `soup train` VRAM pre-flight now passes padded SFT runs it refused before (#2934).** For a text SFT run that pads each micro-batch to its longest row (the transformers backend, no packing, multipack, streamed data or layer streaming) whose estimate at `data.max_length` does not fit the card, the refusal is held back until the data is loaded; before a run is registered the longest row of the train and validation splits is measured with the trainer's own tokenisation (the base model's tokenizer, the chat template, `data.chat_template`, truncation at `data.max_length`; no model is loaded), and the run is priced at that length. A run that fits there starts, and the pre-flight prints one line with both numbers (`priced at 79 tokens, the longest row; data.max_length is 1024`); one that still does not fit is refused as before, with both numbers on the panel. Qwen3-0.6B with LoRA r16 on rows of at most 79 tokens was priced at 9,718 MiB (10.19 GB) at `data.max_length` 1024 against 2,108 MiB allocated, and refused on an 8 GB card. For a held-back run the verdict comes after the data is loaded and before the run is registered, and the "Start training?" prompt follows the verdict instead of preceding it. At most 20,000 rows and 90 seconds are read, because a sample is not a maximum: past either, or with no readable tokenizer, a model that ships its own code, or data that is not chat messages, the run is priced at `data.max_length` as before and the panel says why. A run that already fits reads nothing; a run that would not fit even at 64 tokens, every other task, backend and modality, packed or streamed data, a run that only warns outside the calibrated range, and `--allow-oom-attempt` are decided as before. No run is refused that was not refused before (the decision to refuse stays the one made at `data.max_length`; a test compares the old and new decision over 1,440 pre-flights), and the estimate, `soup profile` and the MCP `profile` tool print the numbers they printed.

- `soup ship` writes its audit trail: a live `--task-mode metric` or `judge_score` run with `--output verdict.json` now also writes `verdict.task-rows.jsonl` (only with `--output`; `--emit-evidence` alone writes nothing new), one JSON line per task row with the prompt, the expected text, both answers, both scores in [0, 1], whether each answer hit the token cap, whether a generation failed, and whether the row got better, worse or stayed the same, so a verdict can be checked row by row. The mean of each score column, added up left to right in `index` order and divided by the row count, is the reported `task_win.base` / `task_win.tuned` exactly for `metric` and within 1e-12 for `judge_score`, whose reported number is still the judge's own (no verdict changes); `soup_cli.utils.ship_task_rows.load_task_rows` reads the file back strictly. `--output` gains `task_rows` (the file's bare name, or `null`) and the evidence a `task_rows` pointer when it sits beside `--output`; no key is removed or renamed. The file holds your prompts and answers, so it stays local: it is never part of the verdict, the evidence or the `--push` comment, it is mode 0600 on POSIX and inherits its folder's permissions on Windows, and a run killed while writing can leave a `.soup.*.tmp` file with partial rows beside it. Migration: a failed write of the file ends a SHIP with exit 1 after the verdict is written (a DON'T SHIP keeps exit 2), and an `--output` name that cannot carry the file name (its derived name would exceed the file system's limit), that is a network share or a device, whose `.task-rows.jsonl` file already exists and was not written by `soup ship`, or that would make the rows replace one of your own files is refused with exit 3 before any model loads.

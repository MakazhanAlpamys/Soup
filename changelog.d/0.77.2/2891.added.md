- Reinforcement-style runs record their per-step training reward in the experiment tracker, so a program can read a reward curve the way it reads a loss curve: two nullable columns, `metrics.reward` (the batch's mean reward) and `metrics.reward_std` (its spread, where the trainer logs one), added in place after the existing columns of `~/.soup/experiments.db`. `soup train` fills them from TRL's `reward` / `reward_std` (GRPO) and `objective/scores` (PPO, and online DPO scored by a reward model or function), by exact key name; a PPO log, which carries no `loss`, now writes a row for its reward. NULL means "not measured": every other run, a row that logged no reward, and a value that is not a finite number. `soup runs show` and `soup runs compare` print the reward only for a run that has one, `GET /api/runs/{run_id}/metrics` returns both columns, and the live `metric` event carries them when set. `benchmark:reward` and `benchmark:reward_std` are refused as evaluation metrics, like `benchmark:val_reward`. Databases written before this change read NULL; a database written after it stays readable by 0.77.2. (#2891)

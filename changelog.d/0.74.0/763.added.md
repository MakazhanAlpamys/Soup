- **`soup adapters audit` checks whether a finished run did what its config asked (#762 by @Srinivasan8888 in #763).** The MLX path records its effective settings in `adapter_config.json` — optimizer, scheduler, warmup and total updates, weight decay, gradient clipping, accumulation, checkpointing and the response-only mask — because each of those was once accepted and silently dropped (#683, #684, #685, #686, #749). Nothing read that record back, so answering "did my run do what I asked?" meant opening two files and comparing by eye. `soup adapters audit ./out --config soup.yaml` prints a per-setting table of asked-versus-ran, explains each divergence, and exits non-zero when any is found, so it composes into CI and `soup ship`; `--json` emits the same result for machine consumption. A setting the record cannot speak to is reported `unknown` and never as agreeing — a false clean bill is worse than no audit — and `unknown` does not fail the command, since an older adapter simply predates the keys. The motivating case is a warmup that rounds away: `warmup_ratio: 0.03` over twelve optimizer updates is zero warmup steps, which the trainer warns about once and the adapter records permanently. On the transformers path only LoRA shape can be checked, because PEFT writes its own `adapter_config.json`, and the command says so rather than implying a clean bill it cannot give.
